# pro-addon/ — JHMG AI Editor for Divi 5 Pro (separate plugin)

The Pro add-on for the free WordPress.org plugin in `wp-plugin/`. It is a **separate plugin**, sold and hosted at divi5lab.com, never shipped in the free zip and never uploaded to WordPress.org. It extends the free plugin only through the `jhmg_aied_*` hooks (`docs/EXTENDING.md`) and calls a small set of the free plugin's classes (pinned by `tests/FreeApiCompatTest.php`).

Spec: `docs/superpowers/specs/2026-10-02-pro-addon-design.md`. Plans: `docs/superpowers/plans/`.

## Preview tokens

`find_replace_site`, `manage_theme_template` and the launch of `build_site` need the token of a dry run of the same arguments (`src/Site/PreviewToken.php`): signed, bound to the arguments, the items' content hashes (or the template's state) and the user who previewed, valid 30 minutes, and spent by the first real run, so an `undo_batch` that puts the previewed content back cannot be followed by a replay. The spent mark is a transient: an object cache that evicts it can make a spent token usable again inside its 30 minutes, for the same user and the same arguments only. A content change since the preview is still caught (the changed-since check), but a replay after an `undo_batch` that restored the previewed content is not; every capability check and `LayoutGate` still run on a replay.

## Site builds (`build_site`)

A build is ONE batch that grows. `add_page` validates one page (`LayoutGate`), refuses a taken slug, creates it as a draft and appends a `page_created` item; the first page opens the build (one open build per user; the first call returns its `build_id`). `launch` is the only step that changes what visitors see: a previewed, single-use-token step that publishes the pages, sets the page flagged `is_front` and rebuilds the "Main Menu" from the published `in_menu` pages, appending those items to the same batch. `undo_batch` walks it back in reverse (menu, front page, statuses, then the created pages are trashed unless they changed since); it also abandons an open build (the build is closed by the undo even when every page had been edited and nothing could be restored). `build_site` needs `publish_pages`; `launch` additionally needs `edit_theme_options` for the menu and `manage_options` for the front page.

## Global colors (`manage_global_colors`)

Divi's `GlobalData::set_global_colors()` REPLACES the whole custom color map, so the tool always sends the complete map once (untouched entries exactly as Divi returned them) and then reads back what Divi really stored; that read-back, not the request, is what the batch records. The five theme (Customizer) colors live in the theme's own settings: they are sent only when being changed (needs `allow_theme_colors`, bound into the preview token), only their `color` can change, and they are read through their live option because Divi caches them for the whole request. There is no delete (a page citing a missing color silently loses it); `temporary` colors belong to Divi's builder session and are refused. An entry Divi's own sanitiser cannot keep (an empty color) is dropped by any replace-all save: the result lists it as `unexpected_changes`. An entry that Divi itself drops during the save (listed as `unexpected_changes`, reason `removed_by_divi`) is only reported, not recorded in the batch, so `undo_batch` cannot bring it back. Divi 5.14 only emits a custom color's `--gcid-` CSS variable on pages (or Theme Builder templates) that cite it, so a new color shows nowhere until a layout cites it (verified by `make verify-pro-global-colors`). Spec: `docs/superpowers/specs/2026-10-05-pro-global-colors-design.md`; plan: `docs/superpowers/plans/2026-10-05-pro-global-colors.md`.

## Known limits

- WordPress gives draft pages no unique slug and resolves a clash only when a page is published, so `build_site` refuses a taken slug at `add_page`, re-checks at launch (`slug_taken` skips the page) and reports a slug core still changed at publish (`slug_changed`). A menu that points at a draft page shows a dead link to visitors, which is why the menu is only rebuilt at launch.
- With `EMPTY_TRASH_DAYS` set to 0 undoing a build deletes its pages permanently (the undo of that undo is then recorded as unavailable).
- The build lock covers `add_page` and `launch`, not `undo_batch`: an `undo_batch` of an open build while an `add_page` is running can drop the page that call was adding, and one during a launch makes the launch skip (`not_available`) a page it has just trashed, never publish it. A call that takes longer than the lock's 15 seconds can overlap the next one. An abandoned build never expires: undo it with `undo_batch` to start another.
- If the theme or core menu setting "Automatically add new top-level pages" is on, publishing a page adds it to that menu by itself; those items are not recorded, so an undo of the launch can report such a page `in_use` and keep it published until you remove it from that menu.
- `add_page` puts a page in the menu by default only for users who may edit menus (`edit_theme_options`); a page flagged for the menu or the front page by someone without those permissions is refused at `add_page`, because the launch could never apply it.

- The audit's link check cannot tell a missing page from an archive or custom route (the finding says so), and reads at most 200 links per item (`LINKS_NOT_ALL_CHECKED`).
- On a site with more than 1000 Divi 5 pages `audit_site` audits the first 1000 (by id) and says so, and `find_replace_site` refuses and asks for `page_ids`.
- The ChatGPT importer allows 30 operations in total: 16 free + 14 Pro = 30, so the budget is used up. The 15th Pro tool, `manage_global_colors`, is MCP + REST only on purpose (`ProOpenApi::MCP_REST_ONLY`; `ProParityTest` and `ToolsTest` pin the exception). Any further tool needs the same owner decision or a merge of two tools.
- The `verify-pro-*` scripts create and delete throwaway content (`verify-pro-rest` is read-only): all nine refuse to run unless the site host is localhost, 127.0.0.1, ::1, `*.local`, `*.test` or `*.localhost` (`scripts/dev-guard.php`).

## Dev override of the licence server

`AIED_PRO_API_BASE` redirects the licence key to another host, so it is honoured only when `wp_get_environment_type()` is `local` or `development`; anywhere else it is ignored and `https://divi5lab.com` is used.

## Undo, in one paragraph

Every Pro write is a batch of items. `undo_batch` restores each item whose target still looks the way the batch left it (the changed-since rule; `force` overrides only that), reports the rest (`changed_since`, `no_undo_point`, `forbidden`, `failed`) and says "fully undone" only when every item restored. Page-content items rely on the free plugin's history (10 snapshots per page), so a very old batch may be only partly undoable. Menu undo restores titles, links, nesting, classes, target, title attribute, XFN and description, not custom meta added by other plugins. Header/footer and template items re-check, at undo time, that the layout or template is still a live Theme Builder one, the user's Theme Builder permission and `edit_theme_options`; a change made in Divi's own builder afterwards is never overwritten. Known limitation (free plugin 4.4.0 and older): the dashboard 'recent versions' list also shows header/footer edits made by these tools, but its Restore button only works for pages; free 4.5.0 hides those rows. Undo a header or footer change with `undo_batch`.

## `staged-4.3.0/`

The `src` and `tests` files are verbatim copies of the 4.4.0-tree files for header/footer editing. `4.3.0-free-plugin.diff` is the original 4.3.0 merge diff (837b712), whose handler and guide hunks predate the 4.4.0 edits to the same files; the free re-cut's own removal commits (5cf40c0, fd4e50d, cd5fffe) are the exact current removal hunks. Not run, not shipped. `ThemeLayouts` and the layout half of `EditTarget` were ported into `src/ThemeBuilder/` in 0.3.0; this folder stays as the record of the 4.3.0 spike.

## Contract

It must not need any change to the free plugin beyond the documented hooks. Nothing here is ever loaded by the free plugin's zip, and `phpunit.xml` at the repo root never scans this folder.
