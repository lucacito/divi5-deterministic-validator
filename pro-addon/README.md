# pro-addon/ — JHMG AI Editor for Divi 5 Pro (separate plugin)

The Pro add-on for the free WordPress.org plugin in `wp-plugin/`. It is a **separate plugin**, sold and hosted at divi5lab.com, never shipped in the free zip and never uploaded to WordPress.org. It extends the free plugin only through the `jhmg_aied_*` hooks (`docs/EXTENDING.md`) and calls a small set of the free plugin's classes (pinned by `tests/FreeApiCompatTest.php`).

Spec: `docs/superpowers/specs/2026-10-02-pro-addon-design.md`. Plans: `docs/superpowers/plans/`.

## Preview tokens

`find_replace_site`, `manage_theme_template` and the launch of `build_site` need the token of a dry run of the same arguments (`src/Site/PreviewToken.php`): signed, bound to the arguments, the items' content hashes (or the template's state) and the user who previewed, valid 30 minutes, and spent by the first real run, so an `undo_batch` that puts the previewed content back cannot be followed by a replay. The spent mark is a transient: an object cache that evicts it can make a spent token usable again inside its 30 minutes, for the same user and the same arguments only. A content change since the preview is still caught (the changed-since check), but a replay after an `undo_batch` that restored the previewed content is not; every capability check and `LayoutGate` still run on a replay.

## Site builds (`build_site`)

A build is ONE batch that grows. `add_page` validates one page (`LayoutGate`), refuses a taken slug, creates it as a draft and appends a `page_created` item; the first page opens the build (one open build per user; the first call returns its `build_id`). `launch` is the only step that changes what visitors see: a previewed, single-use-token step that publishes the pages, sets the page flagged `is_front` and rebuilds the "Main Menu" from the published `in_menu` pages, appending those items to the same batch. `undo_batch` walks it back in reverse (menu, front page, statuses, then the created pages are trashed unless they changed since); it also abandons an open build (the build is closed by the undo even when every page had been edited and nothing could be restored). `build_site` needs `publish_pages`; `launch` additionally needs `edit_theme_options` for the menu and `manage_options` for the front page.

## Global colors (`manage_global_colors`)

Divi's `GlobalData::set_global_colors()` REPLACES the whole custom color map, so the tool always sends the complete map once (untouched entries exactly as Divi returned them) and then reads back what Divi really stored; that read-back, not the request, is what the batch records. The five theme (Customizer) colors live in the theme's own settings: they are sent only when being changed (needs `allow_theme_colors`, bound into the preview token), only their `color` can change, and they are read through their live option because Divi caches them for the whole request. There is no delete (a page citing a missing color silently loses it); `temporary` colors belong to Divi's builder session and are refused. An entry Divi's own sanitiser cannot keep (an empty color) is dropped by any replace-all save: the result lists it as `unexpected_changes`. An entry that Divi itself drops during the save (listed as `unexpected_changes`, reason `removed_by_divi`) is only reported, not recorded in the batch, so `undo_batch` cannot bring it back. Divi 5.14 only emits a custom color's `--gcid-` CSS variable on pages (or Theme Builder templates) that cite it, so a new color shows nowhere until a layout cites it (verified by `make verify-pro-global-colors`). Spec: `docs/superpowers/specs/2026-10-05-pro-global-colors-design.md`; plan: `docs/superpowers/plans/2026-10-05-pro-global-colors.md`.

## Global variables (`manage_global_variables`)

Divi's `GlobalData::set_global_variables()` REPLACES the whole variables map, so the tool sends the complete map once and records the read-back, not the request. Only `numbers` and `strings` variables are written (values are checked strictly; there is no delete, only `archived`); every other group (`images`, `links`, `fonts`, `gradients`) is passed back untouched. A stored `colors` group, or an entry Divi's own sanitiser would drop, makes the call refuse with the reason and write nothing. Divi silently ignores a save without the Variables Manager permission, so the tool checks it (and `edit_theme_options`) up front. A created variable shows nowhere until a layout cites it; teaching an assistant to cite variables is not built yet (phase B of the spec). Real runs and real undos hold a site-wide lock from before the first read. Spec: `docs/superpowers/specs/2026-10-06-pro-global-variables-design.md`; plan: `docs/superpowers/plans/2026-10-06-pro-global-variables.md`; evidence: `docs/global-variables-evidence-5.14.md`; live gate: `make verify-pro-global-variables`.

## Module presets (`manage_global_presets`)

The tool creates and updates Divi module presets (for example a heading style that pages cite with `modulePreset: ["<id>"]`) and never deletes one. Divi's PHP preset functions check no capability, so the tool checks `edit_theme_options` itself. Creates go through Divi's own ADDITIVE import (`process_presets_for_import`), which never touches an existing preset; the new items are found by the set difference of the stored item ids around each import (the import's id-mapping format is not relied on). Updates hand Divi's complete-data save one full data set with the preset's `attrs` and `styleAttrs` replaced and `updated` set; `renderAttrs`, `version`, `type` and `created` are kept. A module that had no presets also gets a default preset from Divi on its first import: the dry run says so, the result lists it, and `undo_batch` removes it again (and the module entry it created), unless anyone added a preset to that module since, in which case the undo of the create is refused. Updating a module's DEFAULT preset restyles every module of that type that has no preset of its own, so it needs `allow_default_presets` (bound into the preview token); it also works on Divi's empty default shells (a default preset stored without attrs), and undoing that update puts the shell back. Custom CSS, scripts and unsafe style values in a preset's attributes are refused by the same `CodePolicy` the layout gate uses (run over one synthetic block of that module), because presets bypass `LayoutGate`. Legacy preset data (a module entry that is not a normal `divi/...` key, an item without a matching `moduleName`) is carried through untouched and refused as a target; `group` (option-group) presets are carried through untouched and not managed. Real runs and real undos hold a site-wide lock from before the first read, and the result is read back: that read-back, not the request, is what the batch records. A run with nothing to change answers without a token. Divi code is only reached through the class named by `GlobalPresets::PRESET_CLASS`, never by a literal call or a raw option name (`ProSafetyScanner`). Spec: `docs/superpowers/specs/2026-10-06-pro-global-presets-design.md`; evidence: `docs/global-presets-evidence-5.14.md`; live gate: `make verify-pro-global-presets` (it temporarily restyles the site's real heading default preset and restores it).

## Custom fields (`set_custom_fields`)

The tool sets custom field values on ONE post the user can edit (any public post type: pages, Divi Projects, blog posts, products). The free plugin only reads fields (`get_custom_fields`) and never writes post meta; the writing lives here. Keys must be ones the site already knows: an ACF field, or a key at least one post already has (the check looks at every post WordPress's own post queries return site-wide, that is any status except trash and auto-drafts and any type not excluded from search, so it can reveal that some post uses a key; secret and hidden keys are refused first). The key "0" is refused outright, so an assistant cannot invent keys. A key ACF manages that this tool cannot see in ACF's field list (for example a clone member) is refused, and so is a field whose current value is over 512 KB. The key must be printable ASCII (at most 191 characters), show up in `get_custom_fields` (never a `_` key, a WordPress-protected key or a secret-looking one), pass `edit_post_meta`, be stored once on the post, and match an existing key's letter case exactly. A value is a string of at most 10,000 characters with no custom code (`<script`, `<style`, `<iframe`, `<?`, `javascript:` URLs, event-handler attributes; `FieldValuePolicy`) and nothing `wp_kses_post()` would silently change (a bare `&` is fine; a plain `<` or `>` in text is refused because WordPress markup filtering entity-encodes it). ACF `url` fields must start with `http://`, `https://` or `//`, and `email` fields must look like an address. For an ACF field the type decides: plain-string types, numbers, choices (`select` with one value, `radio`, `button_group`) and `true_false` are accepted; every other ACF type (repeaters, relationships, images, checkboxes, passwords and the like) is refused with "edit this field in the ACF editor". Up to 25 fields per call, no duplicate key.

All-or-nothing: if any field is refused, nothing is written and every reason is reported. A write that fails, or does not read back as sent, is rolled back together with the fields already written. `dry_run: true` runs every check and shows each field's before and after; it writes nothing and records no batch, and needs no preview token (one post, at most 25 fields). A real run records ONE batch of `post_meta` items; `undo_batch` restores each old value, or deletes a key the call created, and refuses a field whose value was changed since (the changed-since rule); the batch counts as fully undone only when every field was restored. If a rollback cannot restore a field, the error names the fields that may not have been restored (check them with `get_custom_fields`). If the writes succeed but the batch cannot be recorded, the writes stay and the answer carries a `batch` entry with `id: null` and `undoable: false` saying so: `undo_batch` cannot undo that change.

MCP + REST only, on purpose: the 30-operation ChatGPT budget is used up, so `set_custom_fields` is the fourth tool in `ProOpenApi::MCP_REST_ONLY`. Spec: `docs/superpowers/specs/2026-10-09-set-custom-fields-design.md`; live gate: `make verify-pro-custom-fields` (the ACF checks run when the free ACF plugin is active, otherwise they are SKIP lines).

Release note: raise `Compat::MIN_FREE` to the first free version that contains `FieldTarget`, `CustomFieldReader` and `CustomFields` when you version the free release (the runtime guard `REQUIRED_CLASSES` already switches the Pro tools off if they are missing).

## Create products (`create_product`)

The tool creates up to 25 new SIMPLE WooCommerce products per call, always as DRAFTS. It needs WooCommerce active, the `edit_products` permission (plus `assign_product_terms` when a product uses categories or tags), and `edit_posts` like the other Pro tools. Arguments: `products` (a list of 1 to 25 objects) and an optional strict boolean `dry_run`. Each product takes only these fields (any other key is refused):

| Field | Rule |
|---|---|
| `name` (required) | plain text, at most 200 characters, no control characters, no `<` or `>`, no backslash (WordPress drops it), no leading or trailing spaces; a bare `&` is fine |
| `description`, `short_description` | string, at most 10,000 / 1,000 characters, no custom code (`FieldValuePolicy`) and nothing `wp_kses_post()` would change, no backslash |
| `sku` | 1 to 100 printable ASCII characters, no `<` or `>`; must not be used by another product or twice in the call |
| `regular_price`, `sale_price`, `weight` | decimal string such as `"20"` or `"20.50"` (no currency symbol); `sale_price` needs a `regular_price` and must be lower |
| `manage_stock`, `stock_quantity`, `stock_status`, `backorders` | with `manage_stock: true` a whole `stock_quantity` (0 to 1,000,000) is required and `backorders` is `no`, `notify` or `yes`; without it `stock_status` is `instock`, `outofstock` or `onbackorder` and the other two are refused |
| `categories`, `tags` | lists of EXISTING slugs (at most 10 / 20); an unknown slug is refused, never created |
| `image_id`, `gallery_image_ids` | Media Library images the user may use (gallery at most 10); no URLs are accepted |
| `dimensions` | object with only `length`, `width`, `height` (decimal strings) |
| `tax_status` | `taxable` (default), `shipping` or `none` |
| `virtual`, `sold_individually` | booleans |

All-or-nothing: every product is checked first, and one refused product creates nothing; the answer lists every reason with the product's position and name. After the checks each product is saved and read back; a failed save, or any difference between what was asked and what WooCommerce stored (name, SKU, prices, stock, terms asked for, images and the draft status), removes every product this call created. WooCommerce may add its default category to a product saved without categories, which is not counted as a difference. If a product's row was inserted before its save failed and cannot be removed, the error names it (or says a draft may have been left behind) so you can check or trash it. A failed save deletes only a post that is provably the draft this save inserted (`InsertedProduct`); one honest residual remains: if another plugin's hook inserts a draft product with exactly the same name during our save and our own insert never happens, that foreign draft is deleted and the tool says "Nothing was created." `dry_run: true` runs every check and shows what would be created; it creates nothing and records no batch.

A real run records ONE batch of `product_created` items. `undo_batch` moves each created product to the trash, but only while it is still a draft that matches what the call saved (the changed-since rule, which compares every field the call read back, tags, images, weight and the rest included): a product edited in any way, published or trashed since is skipped and reported. With `EMPTY_TRASH_DAYS` set to 0 the trash is a permanent delete, so a changed product is never deleted, `force` or not. Undoing records a `product_trashed` item, so the undo can itself be undone (a trashed product comes back as a draft).

Out of scope on purpose: variable, grouped, external and downloadable products, publishing, changing or deleting an existing product, creating categories, tags or images, and any argument that is a URL. MCP + REST only: the 30-operation ChatGPT budget is used up, so `create_product` is the fifth tool in `ProOpenApi::MCP_REST_ONLY`. Spec: `docs/superpowers/specs/2026-10-13-pro-create-product-design.md`; live gate: `make verify-pro-create-product`.

## Update products (`update_products`)

The tool changes EXISTING simple, external and variable WooCommerce products, and the price and stock of a variable product's variation rows. It needs WooCommerce active, `edit_products`, `edit_post` on every product (plus `assign_product_terms` when categories or tags are given) and `edit_posts` like the other Pro tools. Arguments: `updates` (1 to 25 objects, each `{ "id": <product>, ...fields }`), a strict boolean `dry_run` and a `token`. An omitted field is left alone, `""` clears a text, the SKU, a price, a sale date or the weight, a list replaces the whole set, an unknown key is refused by name.

| Group | Fields and rules |
|---|---|
| Prices and sale window | `regular_price`, `sale_price` (decimal strings), `sale_from`, `sale_to` (`YYYY-MM-DD`). Judged against the RESULTING state: a sale price needs a regular price and is lower; sale dates need a sale price; `sale_to` is not before `sale_from`. A sale starts at 00:00:00 of its first day and ends at 23:59:59 of its last (site time zone). Not available on a variable product itself (use its variation rows). |
| Stock | `manage_stock`, `stock_quantity` (0 to 1,000,000), `stock_status`, `backorders`. A quantity needs managed stock, managed stock needs a quantity, `stock_status` is refused while stock is managed. External products have no stock fields. |
| Text and catalogue | `name`, `description`, `short_description`, `sku`, `categories`, `tags`, `image_id` (0 removes it), `gallery_image_ids`, `weight`, `dimensions` (only the axes given change), `tax_status`. The same rules as `create_product`; the SKU may be the product's own. |
| Variation rows | `variations`: up to 100 objects `{ "id": <variation of this product>, regular_price, sale_price, sale_from, sale_to, manage_stock, stock_quantity, stock_status, backorders }`; at most 200 rows per call. |

Never changed: status (publish, draft, private, trash), type, slug, grouped products, attributes, the variations themselves (nothing is created or deleted), tax and shipping classes, downloads, upsells, any other meta.

**Preview and token.** `dry_run: true` validates everything (all or nothing: every reason comes back, each refusal prefixed with the product's position and id, and its name where it can be read, e.g. `Product 2 (#51 "Plain Mug")` or `Product 2 (#999)`, cut at 6,000 characters) and returns, per product, a before and after of only the fields that would change, plus ONE `token`. A real run needs that token (single use, 30 minutes, same user, same arguments). The token carries a hash of each product's whole current state, variation rows included: a product that changed since the preview is SKIPPED and reported (`changed_since_preview`), the others proceed. A refused run keeps its token; it is spent once all checks pass, just before anything is saved. A scheduled sale (`sale_from` in the future) leaves the price at the regular price until WooCommerce's own scheduler starts it; the preview says so in `notes`.

**Apply, read back, roll back.** Products are saved one at a time; each is read back and compared (texts through `ProductValuePolicy::sameText`, so core's `&amp;` is the same text; prices, weight and dimensions as numbers ("20" equals "20.00"), dates and the other fields exactly; categories: a requested set must match exactly, an empty one accepts the store's default; derived values such as a variable parent's price or a managed product's stock status are not compared). A failed save or a difference puts every product the run touched back, records NO batch and answers with a safe message (only this add-on's own texts and WooCommerce's data-exception text are shown). A change to a text whose current value is over 512 KB (or not valid UTF-8) is refused (the whole call, as every refusal), and the previous texts of one call may not exceed 1 MB.

**Undo.** A real run records ONE batch of `product_fields` items. `before` holds the previous values of only the fields that changed, except that wherever `manage_stock` changes (on the product or on a variation row) the whole stock group is recorded (`manage_stock`, `stock_quantity`, `stock_status`, `backorders`, `low_stock_amount`); `after_hash` is the hash of those fields as read back. `undo_batch` restores a product only while those fields still hold what the run wrote (a field the owner changed since keeps the product item back; `force` skips that rule, never a permission or existence check), reads them back, and records the inverse so the undo can be undone. An item is refused with the reason `conflicts` (nothing is written) when restoring the previous prices would make WooCommerce discard a sale price added since, because WooCommerce clears any sale price that is not below the regular price; the owner's sale price stays. If a restore reads back differently, the product is put back and the item fails (`restore_differs`).

MCP + REST only: the 30-operation ChatGPT budget is used up, so `update_products` is the sixth tool in `ProOpenApi::MCP_REST_ONLY`. Spec: `docs/superpowers/specs/2026-10-13-pro-update-products-design.md`; live gate: `make verify-pro-update-products`. Known limits: two real runs racing each other are not serialised (WooCommerce's own admin has the same property); a persistent object cache can show stale reads right after a save; a sale window is kept as dates only, so a sale time other than 00:00:00 / 23:59:59 set elsewhere comes back at those times after a rollback or an undo.

## Known limits

- WordPress gives draft pages no unique slug and resolves a clash only when a page is published, so `build_site` refuses a taken slug at `add_page`, re-checks at launch (`slug_taken` skips the page) and reports a slug core still changed at publish (`slug_changed`). A menu that points at a draft page shows a dead link to visitors, which is why the menu is only rebuilt at launch.
- With `EMPTY_TRASH_DAYS` set to 0 undoing a build deletes its pages permanently (the undo of that undo is then recorded as unavailable).
- The build lock covers `add_page` and `launch`, not `undo_batch`: an `undo_batch` of an open build while an `add_page` is running can drop the page that call was adding, and one during a launch makes the launch skip (`not_available`) a page it has just trashed, never publish it. A call that takes longer than the lock's 15 seconds can overlap the next one. An abandoned build never expires: undo it with `undo_batch` to start another.
- If the theme or core menu setting "Automatically add new top-level pages" is on, publishing a page adds it to that menu by itself; those items are not recorded, so an undo of the launch can report such a page `in_use` and keep it published until you remove it from that menu.
- `add_page` puts a page in the menu by default only for users who may edit menus (`edit_theme_options`); a page flagged for the menu or the front page by someone without those permissions is refused at `add_page`, because the launch could never apply it.

- The audit's link check cannot tell a missing page from an archive or custom route (the finding says so), and reads at most 200 links per item (`LINKS_NOT_ALL_CHECKED`).
- On a site with more than 1000 Divi 5 pages `audit_site` audits the first 1000 (by id) and says so, and `find_replace_site` refuses and asks for `page_ids`.
- The ChatGPT importer allows 30 operations in total: 16 free + 14 Pro = 30, so the budget is used up. The 15th to 20th Pro tools, `manage_global_colors`, `manage_global_variables`, `manage_global_presets`, `set_custom_fields`, `create_product` and `update_products`, are MCP + REST only on purpose (`ProOpenApi::MCP_REST_ONLY`; `ProParityTest` and `ToolsTest` pin the exception). Any further tool needs the same owner decision or a merge of two tools.
- The `verify-pro-*` scripts create and delete throwaway content (`verify-pro-rest` is read-only): every one of them refuses to run unless the site host is localhost, 127.0.0.1, ::1, `*.local`, `*.test` or `*.localhost` (`scripts/dev-guard.php`).

## Dev override of the licence server

`AIED_PRO_API_BASE` redirects the licence key to another host, so it is honoured only when `wp_get_environment_type()` is `local` or `development`; anywhere else it is ignored and `https://divi5lab.com` is used.

## Undo, in one paragraph

Every Pro write is a batch of items. `undo_batch` restores each item whose target still looks the way the batch left it (the changed-since rule; `force` overrides only that), reports the rest (`changed_since`, `no_undo_point`, `forbidden`, `failed`; a failed item carries its `reason`, e.g. `conflicts` for a product restore that would lose a sale price) and says "fully undone" only when every item restored. Page-content items rely on the free plugin's history (10 snapshots per page), so a very old batch may be only partly undoable. Menu undo restores titles, links, nesting, classes, target, title attribute, XFN and description, not custom meta added by other plugins. Header/footer and template items re-check, at undo time, that the layout or template is still a live Theme Builder one, the user's Theme Builder permission and `edit_theme_options`; a change made in Divi's own builder afterwards is never overwritten. Known limitation (free plugin 4.4.0 and older): the dashboard 'recent versions' list also shows header/footer edits made by these tools, but its Restore button only works for pages; free 4.5.0 hides those rows. Undo a header or footer change with `undo_batch`.

The `src` and `tests` files are verbatim copies of the 4.4.0-tree files for header/footer editing. `4.3.0-free-plugin.diff` is the original 4.3.0 merge diff (837b712), whose handler and guide hunks predate the 4.4.0 edits to the same files; the free re-cut's own removal commits (5cf40c0, fd4e50d, cd5fffe) are the exact current removal hunks. Not run, not shipped. `ThemeLayouts` and the layout half of `EditTarget` were ported into `src/ThemeBuilder/` in 0.3.0; this folder stays as the record of the 4.3.0 spike.

## Contract

It must not need any change to the free plugin beyond the documented hooks. Nothing here is ever loaded by the free plugin's zip, and `phpunit.xml` at the repo root never scans this folder.
